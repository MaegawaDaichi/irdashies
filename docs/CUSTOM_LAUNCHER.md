# Custom版の起動ランチャー

`launch-custom.cmd` をダブルクリックすると、PC内の現在のソースを確認し、
必要なときだけパッケージを作り直してアプリを起動します。インストーラーは作りません。

## 初回

1. この変更を `test` に取り込み、Windows PCでpullします。
2. Node.js 24以上、Git、Python、Visual StudioのC++ビルド環境を用意します。
3. 公式版・インストール済みCustom版・`npm start`で起動したアプリを終了します。
4. リポジトリ直下の `launch-custom.cmd` をダブルクリックします。
5. 既存ショートカットのリンク先を、その `launch-custom.cmd` に変更します。

初回は依存関係の準備とビルドで時間がかかります。次回からはソースが同じなら
ビルドせず起動します。変更確認ではファイルを読むため、待ち時間が完全にゼロには
なりません。表示中のコマンド画面は、起動が成功すると閉じます。

## 更新時

普段どおりマージ・pullした後、同じショートカットから起動してください。
未コミットのソースも比較します。ブランチ名やコミット番号が変わっただけで
ビルド対象の内容が同じなら、再ビルドしません。

- 依存関係が変わった場合・初回・node_modulesがない場合は `npm ci`。
- 再パッケージが必要なら、まず `npm run irsdk:build` を実行。
- 続いてWindows x64向けの `npm run package` を実行。
- すべて成功したものだけを起動用フォルダーに反映。

ネイティブビルドは、再パッケージする際には毎回行う単純な構成です。
通常の起動ではLint・全テスト・Gitのpull/push・マージ・バージョン変更は行いません。
それらの検証は機能を取り込む際に別途行ってください。

## 保存先と失敗時の動作

生成物と比較用の記録は `.cache/custom-launcher/` に保存します（Git管理対象外）。
`app/` が現在のパッケージ、`previous/` が前回のパッケージです。
ユーザーの設定保存先やアプリのバージョン番号は変更しません。
インストール済みCustom版と設定を共有するため、同時起動は避けてください。

ビルド失敗時はエラーを表示して停止し、前回のアプリを更新版として起動しません。
前回成功したパッケージは残ります。アプリ実行中に再ビルドが必要になった場合は、
トレイから終了して再度ランチャーを開いてください。
二重起動されたランチャーはビルドを重複実行せず停止します。

ビルド中にPCが停止した場合など、ランチャーが動いていないのにロックエラーが
出るときだけ `.cache/custom-launcher/lock` を削除して再実行してください。
強制的に再ビルドしたいときは、アプリを終了し、
`.cache/custom-launcher/state.json` を削除します。

比較対象は `src`、`tools`、アセット、packageファイル、ビルド設定などです。
Gitで無視されたファイルや、外部の環境変数・Windowsビルドツールの変更は比較しません。
これらを変更した場合も、上記の方法で強制再ビルドしてください。

## ランチャーの検証

```sh
node --test tools/check-launch-custom.mjs
```

ビルドと起動を代替処理に置き換えたテストです。実際のWindows上での初回ビルドと
起動確認は別途必要です。
